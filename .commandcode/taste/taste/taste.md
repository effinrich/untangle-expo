# Taste
- Expects audits/reviews to cover all surfaces and platforms, not just the slice the agent initially chooses (e.g. both the web UI and the native/mobile screens) — explicitly pushed back when a design checkup scoped itself to web only and asked for another pass over the screens. Confidence: 0.7
- Wants the agent to commit changes proactively ("commit at will") without pausing to ask for confirmation first — treats a "don't commit unless asked" rule as wrong. Version control is the agent's to drive; pushing/other shared-state actions are a separate matter. Confidence: 0.85
- Tests are the default, not optional: spec-driven development (SDD) and TDD (spec first, then red/green/refactor) drive the work, and every change is expected to arrive with test coverage appropriate to its layer. Never write or keep a rule that says the repo has no test runner, discourages adding test files, or asks permission before adding tests. Confidence: 0.95
- Leaves a long-running dev server (e.g. `bun run web`) untouched and expects the agent to run anything it starts on a separate port rather than disturbing the existing process. Confidence: 0.6
- Never accepts UI/design work as complete without a render check: source reading alone does not count as verification for anything visual. Expects real browser verification (e.g. the Playwright skill driving the live app), not lint + typecheck only — render it, exercise the flows, inspect screenshots/computed styles, then report what actually rendered. This must happen throughout the process, not only at the end: before declaring any visual change done, ask for a screenshot or a look, and state plainly what is still unverified until then. Confidence: 0.9
- Carves out UI/design work from incremental-refactor and minimal-change rules: refactoring UI, look and feel, and aesthetics should be done in broad strokes (repo-wide when warranted), especially when the current state is bad — surface work is loosely coupled and cheaply swappable (like a VS Code theme). The "only touch files you're already changing, leave untouched files alone" rule applies to logic and architecture (low-level routing, backend integration), NOT to visual/aesthetic surface work, and over-engineering concerns apply to functionality (the how and by what means), not to aesthetics. When these expectations are held in repo rule files, the user expects the rule to actually be edited into every coupled copy in one pass rather than just acknowledged in prose. Confidence: 0.9
- Delegates commit/revert triage of the working tree: hands the agent uncommitted work and asks it to evaluate relevance and commit or revert on the agent's own judgment ("evaluate my uncommitted work for relevance, commit or revert accordingly") — uncommitted work should be driven to a conclusion, not left dangling, with only the relevant work paths staged and tooling/agent state (`.cursor/`, `.omc/`, `.commandcode/`) left out of commits. Confidence: 0.7
- Communicates in terse delegative fragments with no restated context (e.g. a bare "yes, lets" approving a proposal from a prior session, or "shall we do a design surface?" picking up a mode the agent recommended earlier) and expects the agent to reconstruct the antecedent — the in-flight proposal — from repo state, handoff/checkup docs, and session history, then act on it rather than asking what was approved. Confidence: 0.7
- Asks for "honest assessment" and means it: wants frank feature-level judgment ("should I even add this?") — including the agent critically re-examining work it just committed itself — rather than validation; and pre-acknowledges known gaps ("I already know the tests need to be added"), so don't restate caveats the user has already conceded — spend the answer on the actual decision. Confidence: 0.7
- When offered a choice between keeping a working-but-overbuilt implementation and a net-deletion simplification, chooses the simplification: approved (bare "yes") deleting a freshly committed launch-count flag, its AsyncStorage key, provider/context wiring, and splash gate in favor of deriving the behavior from the real signal (what the task list looked like on arrival) as one pure two-branch function. Proxy signals + persistence are suspect; deriving from actual state is preferred, even when it means refactoring code committed minutes earlier. Confidence: 0.75
- Unit-test convention established (first non-emulator unit test in the repo, user-endorsed): `bun:test` runner, test files colocated beside the source under test as `*.test.ts` (e.g. `screens/main-screen/utils.test.ts`), with `@types/bun` added as a devDependency so bun tests type-check under `tsc` rather than being excluded from the tsconfig the way `firestore-tests/` is. Confidence: 0.6
- When asked to build a mechanism (e.g. "make a proper error boundary"), the bar is production-grade and fully integrated: use the stack's idiomatic mechanism, not a hand-rolled demo, and wire it into every place it conventionally belongs (web: page root + each workspace section + each modal; native: root layout + every route file) — "implement it throughout and in its expected use case". Confidence: 0.8
- When the agent offers a choice between recommended fixes ("want me to take either?"), approves all of them in one go ("do them both") and adds more scope in the same instruction — execute the full recommended set rather than waiting for per-item selection. Confidence: 0.55
- Faced with a choice between a small self-contained fix that repairs the core loop and going wide with a full diagnosis-then-redesign, chooses the wide path ("yep, 2") — prefers the rebuild to be "one argument rather than a string of patches". Wants bad existing work replaced/discarded as the new work lands ("just wipe away the garbage as the new comes in"), not preserved and patched around. Confidence: 0.6
- Treats the agent's skill/rule set as real leverage and is inclined to expand it ("should I add more of these skills, several are very relevant"), but asks the agent to judge which additions are worth it rather than adding indiscriminately. Confidence: 0.5
- Treats accessibility as a first-class concern run as its own dedicated pass over the UI, not a side effect of other work — invokes standalone interaction and a11y passes (`/design interaction`, `/design a11y`) alongside the broader design work. Confidence: 0.6
- Wants reversibility to live in the object's own state rather than in a separate undo affordance for routine actions: dropped a planned undo for checking off a task on the grounds that the strike-through already makes it reversible ("that's rendered moot by the strikethrough"), and treats undo-vs-confirm as a per-action design call. Confidence: 0.55
- Tracks the open findings from a checkup/audit as an explicit backlog and expects it driven to zero rather than left dangling — closes a session by asking to "wrap up the last bits"; each item should be fixed or deliberately deferred with reasoning, not silently dropped. Confidence: 0.55
- Cares about micro-interaction payoff in the core loop: rejects UI that removes an item abusively/instantly after the user acts on it ("makes it vanish rather abrasively, which robs the user of any satisfaction", "that seems pointless"). Prefers the acted-on object stay put with in-place feedback (strike-through/dim) so the reward lands on it, and prefers user-controlled visibility (a hide/show toggle) over the app force-sorting completed items to the bottom automatically. Confidence: 0.7
- Holds UI work to a flat, undecorated visual language and treats decoration as a tell to be measured down, not a style choice: no `backdrop-blur`, no `shadow-lg/xl/2xl`, no press/scale animations, a single radius token, no uppercase-tracked micro-labels, no dashed frames or icon badges, no emoji in labels, and no nested card/panel boxes — emphasis should come from type size, weight and brightness instead. Repeatedly re-measured these with grep counts ("backdrop-blur 9 -> 0", "active:scale 5 -> 0") as the definition of done. Confidence: 0.6
- Wants the accent colour to have exactly one job per screen — reserved for the single primary action (e.g. amber for "Unstick me"/submit) and deliberately absent from rows and filters, with selection state rendered neutral (background plus a check) so it doesn't compete with the action. Confidence: 0.55
- Prefers native semantic controls over styled chip/pill rows: filters become `<select>`s ("filters are selects, which is what a filter is"), a single-choice picker becomes a real radio group in a `<fieldset>` (earning arrow-key navigation for free), labels go through `sr-only`, and interactive targets are real ~44px hit areas rather than 20px squares. Confidence: 0.55
- Treats context/session state as something to manage deliberately: checks in before starting ("do you need to clear context or anything before starting?") and expects the agent to judge whether a fresh context is warranted and to keep durable state on disk (rules/AGENTS files, design docs, committed code) so a new session needs little priming. Confidence: 0.5
- Reports UI problems by sharing screenshots of the running app rather than describing them in prose (sometimes just dropping an image, or saving it to disk and giving the path) and expects the agent to read the image and trace the visible symptom back to the code that causes it. Confidence: 0.5
- Prefers branch hygiene handled by repository configuration rather than manual cleanup: on being told about a pile of stale branches, chose to set the repo to auto-delete branches on merge ("i can set the repo to delete on merge") instead of having the agent delete them one by one. Confidence: 0.6
- Holds user-facing copy to a plain-language writing rule and expects it enforced repo-wide: no em dashes, no emoji, no marketing sub-headings or filler paragraphs, action labels kept to plain verbs ("Untangle" not "Untangle & Create Micro-Tasks"), and loading states that keep their label instead of replacing it. Confidence: 0.5
- Audits user-facing product terminology for internal consistency and flags mismatches for review, while leaving room for genuinely different concepts — questioned whether on-screen copy should read "micro-tasks" rather than "micro-steps" ("unless it's a wholly different thing"). Expects the agent to check how the term is actually used before renaming, not assume. Confidence: 0.4
- Treats potentially-dead work (stale branches, never-merged PRs) as something to mine for salvage before discarding: wants it reviewed for "anything valuable" and the good parts cherry-picked, while wary of merging branches wholesale if they drag along an unwanted coupled design. Leans toward rescuing value (especially added test coverage) rather than either blind-merging or blind-deleting. Confidence: 0.5
- Defaults to NOT committing per-tool agent/editor state (`.cursor/`, `.omc/`, `.commandcode/`) unless it visibly benefits other developers — asks "is this beneficial for other devs, I'll ignore it all otherwise". Agent preferences/rules should live in the canonical cross-tool home (`AGENTS.md`, mirrored into `.cursor/rules/` and `.windsurf/rules/`) rather than duplicated as a single-tool copy, and a tracked per-run state file that keeps churning should be untracked and `.gitignore`d. Confidence: 0.55
